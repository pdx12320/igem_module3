> 交付对象：队长（用于统合）
> 配套交付：`APOBEC_代码工作流包.zip`（代码，88 个脚本）· 本包（数据）
> 内容：本项目 APOBEC 编辑模块（"保 G 排 A"）**代码包之外的全部项目数据**，共 **6,758 个文件 / 1.63 GiB**，
> 按数据类型分 5 卷。

---

## 1. 为什么分卷

原始数据合计 1.63 GiB。打成单个压缩包在传输上有两个实际问题：
**一是中断后要整包重传**，二是**接收方往往只需要其中一部分**（例如只复核分析结果，不需要 700 MB 的结构预测输出）。
因此按数据类型分卷，每卷自洽、可单独使用。**五卷合起来才是完整数据。**

## 3. 校验完整性

数据总量在 GB 级，传输后**务必先校验**再使用：

```bash
# 1. 解压全部五卷到同一目录，得到与项目工作目录一致的结构
# 2. 校验
sha256sum -c SHA256SUMS.txt          # Linux / macOS / Git Bash
# 或 Windows PowerShell：
#   Get-Content SHA256SUMS.txt | ForEach-Object { ... }   # 见文件内格式说明
```

`MANIFEST.csv` 提供同一份信息的表格版（`relative_path`, `bytes`, `sha256`），
便于用脚本逐项比对，也便于队长统合时按路径定位。

## 6. 使用这些数据前需要知道的三件事

这三条都会直接影响「哪些数字能互相比较」，都写在代码包的 `DATA.md` 里，这里再强调一次：

1. **建库背景未在源表中记录。** 三批补充突变（第二批 37 组、第三批 64 样本）的建库背景与
   更早几批不同，因此**批次之间不能横向比较比值**——只能比较批内的秩。
   建议在源表加一列「建库背景批次」，否则后续无法判断哪些数可以横比。
2. **补充突变源表里 `列1` 的文档定义与算式不符。** 说明写「C388 − C871」，
   实测算式是 `C871 ÷ C388`（连续两批重现）。引用该列前必须确认哪个是 intended。
3. **`c.295` 的 `0` 是「低于检测线」而不是「无数据」，也不等于真实编辑效率为 0。**
   同理，任何 `C871 = 0` 的行，其 +1 比值应判为**不可定义**，不得按 0 参与计算。
